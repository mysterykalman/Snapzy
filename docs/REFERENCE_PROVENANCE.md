# Reference & Donor Provenance

Capture (this repository, built on the Snapzy foundation) draws on several
other repositories during its migration to a full-featured personal
application. This document tracks, per subsystem, which source was
consulted, its license, and how it was used. Update it whenever code is
reused, adapted, or materially informed by an external/donor repository.

- `BrowserBridgeCoordinatorTests` crashed the CI runner's hosted test process with heap corruption. Investigated properly rather than assumed: a temporary diagnostic CI workflow (since deleted) built and ran only that test class with `otool`/`nm`/crash-report collection enabled (tools unavailable in this local environment). Two findings: (1) `BrowserBridgeKit` is genuinely embedded as a separate dynamic-framework copy in both `Snapzy.app/Contents/Frameworks/` and `Snapzy.app/Contents/PlugIns/SnapzyTests.xctest/Contents/Frameworks/` -- real duplicate embedding, but a red herring for this specific crash; (2) the actual symbolicated `.ips` crash report's faulting frame was `BrowserBridgeCoordinator.__deallocating_deinit` -> `swift_task_deinitOnExecutorMainActorBackDeploy`, a Swift concurrency runtime bug in the compiler-synthesized isolated-deinit path for `@MainActor` `ObservableObject` classes, triggered only because these tests were the first code in the repo to deinitialize a transient (non-`.shared`) instance of such a class. Fixed with an explicit `nonisolated deinit {}` on `BrowserBridgeCoordinator` (`Snapzy/Services/BrowserBridge/BrowserBridgeCoordinator.swift`); verified via the same diagnostic workflow before removing the CI skip. The duplicate dynamic-framework embedding noted in (1) is otherwise normal Xcode SPM behavior for a package used by both an app and its hosted test target and was left as-is.
- `BaselineStoreTests` (new this session, see the Baseline/BaselineStore row above) crashed identically. Same investigation standard applied: a temporary diagnostic CI workflow (`debug-baseline-crash.yml`, since deleted) captured 7 real symbolicated `.ips` crash reports. Every one showed the *exact same* runtime frame as the BrowserBridgeCoordinator bug (`swift_task_deinitOnExecutorMainActorBackDeploy`), this time faulting in `DatabaseManager.__deallocating_deinit`, triggered by `BaselineStoreTests.setUpWithError()` deinitializing a locally-scoped `DatabaseManager` returned by `DatabaseManager.openDatabase(at:)`. Root cause: this project builds with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor`, so any class without an explicit deinit (including `DatabaseManager`, which has no annotation making its implicit-MainActor status obvious) gets a compiler-synthesized isolated deinit that hits this Swift runtime bug when a *transient* (non-singleton) instance is deallocated -- `DatabaseManager.shared()` never triggers it because that instance is never deallocated during the app's lifetime. Fixed identically: an explicit `nonisolated deinit {}` on `DatabaseManager` (`Snapzy/Services/Cloud/DatabaseManager.swift`). Verified fixed via the same diagnostic workflow: all 8 `BaselineStoreTests` now run to completion (one unrelated pre-existing test bug found and fixed separately: a fixed-precision-`Date` test fixture change, since GRDB's date storage is millisecond-resolution and cannot round-trip `Date()`'s sub-millisecond precision). This also explains the pre-existing (already skipped before this session) `SnapzyTests/DatabaseManagerTests`, whose `testOpenDatabase_createsDatabaseWithoutThrowing` discards a transient `DatabaseManager.openDatabase(at:)` result the same way -- now un-skipped in `.github/workflows/ci.yml` since the same fix resolves it.
